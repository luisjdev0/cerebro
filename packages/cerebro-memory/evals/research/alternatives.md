# Phase 0 — Research on alternatives to building from scratch (KnowledgeOS)

Research date: 2026-08-06
Scope: evaluate whether **mem0**, **Zep/Graphiti** or **Letta** already solve KnowledgeOS's core problem — **cross-context contamination** in personal memory retrieval (e.g. "Expense Tracker" the software project vs. "personal finances" the life domain, which share vocabulary and confuse a flat semantic search).

> Methodology: web search and reading of official documentation, GitHub repos, issues/discussions and third-party technical blogs, as of August 2026. Every claim carries a reference URL. Where the documentation is ambiguous or contradictory (it happened with mem0 and with Zep) this is pointed out explicitly and the most authoritative source (official repo/PR/issue) is cited.

---

## 1. mem0 (mem0ai/mem0)

### 1.1 Project status
- Very active, ~48K+ GitHub stars, **Apache 2.0** license for the open source SDK/server ([LICENSE](https://github.com/mem0ai/mem0/blob/main/LICENSE), [repo](https://github.com/mem0ai/mem0)).
- "Open-core" business model: free OSS SDK/server + **Mem0 Platform** (cloud, with paid plans and a free tier of 10K memories/month) ([atlan.com](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/)).
- **Critical finding**: in 2026, mem0 **removed Graph Memory from the open source SDK entirely** (PR #4805, "port v3 pipeline with hybrid search, entity extraction, and additive scoring"). The `mem0/graphs/` directories, Neo4j/Memgraph support as a graph store, and the `enable_graph`/`graph_store` config options were deleted. A July 2026 issue (#6591) confirms that even the internal documentation (`AGENTS.md`) kept referencing graph memory as if it existed, when it no longer exists in the code ([issue #6591](https://github.com/mem0ai/mem0/issues/6591)). This contradicts third-party guides and older blog posts (including mem0's own official Docker self-hosting blog) that still show a Neo4j container as part of the stack — evidence that mem0's documentation is outdated/inconsistent with itself ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)).
- The official Platform vs OSS comparison page (`docs.mem0.ai/platform/platform-vs-oss`) still lists "Graph memory: ✅ Built-in (Platform) / ✅ External graph store (OSS)", which directly conflicts with the removal PR — that is, **mem0's own documentation contradicts itself in August 2026**. The most reliable source is the source code and the tracking issue, which confirm total removal in OSS.
- The self-hosted version is **not complete** compared to cloud: authentication/login, memory decay (v3), temporal reasoning (v3), webhooks, export, dashboard, analytics, auto-scaling and high availability are missing — all of it is exclusive to Platform ([docs.mem0.ai/platform/platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss) via WebFetch; indirectly confirmed in [GitHub Discussion #3112](https://github.com/mem0ai/mem0/discussions/3112)).

### 1.2 Self-hosted deployment requirements
- Official Docker stack (blog guide): 3 containers — FastAPI API, **Postgres + pgvector** (default vector store) and (historically) Neo4j for the graph — but the graph no longer applies to OSS, so the real minimum stack today is **API + Postgres/pgvector** ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)).
- LLM required for fact extraction: OpenAI by default (`gpt-5-nano` for extraction, `text-embedding-3-small` for embeddings), with a local alternative via Ollama (`llama3.1`) to run offline ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)).
- RAM: the same guide says a t3.medium instance (2 vCPU / 4 GB RAM) is the viable minimum running Neo4j + pgvector + API together; for real load they recommend t3.large (8 GB). Without Neo4j (no longer needed in OSS) the footprint drops considerably — it is estimated to fit comfortably in a 4 vCPU/8GB VPS next to Postgres, especially if the extraction LLM is remote (API) and not local.
- Supports 20+ vector stores (Qdrant, Chroma, Milvus, Pinecone, pgvector, etc.), which gives infrastructure flexibility ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)). There are reports of real friction: outdated Qdrant version pin (mem0 asked for 1.13.0 while Qdrant was at 1.17.0), auto-recall silently dropping memories, embeddings ignoring the configured `baseURL`, and missing provider SDKs that break startup ([atlan.com](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/), [GitHub Discussion #3112](https://github.com/mem0ai/mem0/discussions/3112)).

### 1.3 Memory model
- **Vector** collection (Postgres/pgvector, Qdrant, etc.) as the central structure. The graph no longer exists in OSS (see 1.1).
- LLM extraction pipeline that produces "memory candidates" and applies one of four operations to them — **A.U.D.N.: ADD, UPDATE, DELETE, NONE** — comparing each new fact against semantically similar existing memories ([memo.d.foundation/breakdown/mem0](https://memo.d.foundation/breakdown/mem0), [arxiv.org/html/2504.19413v1](https://arxiv.org/html/2504.19413v1)).
- Third-party documentation describes conceptual sub-types — episodic memory (interaction summaries), semantic (facts/preferences) and procedural (workflows) — but this is an external interpretation layer, not an explicit, primary data type in mem0's schema ([47billion.com](https://47billion.com/blog/ai-agent-memory-types-implementation-best-practices/), [digitalapplied.com](https://www.digitalapplied.com/blog/agent-memory-architectures-vector-graph-episodic)). The graph (when it existed) did have entity typing (Person, Location, Event, etc.) but that no longer applies to OSS.

### 1.4 Context isolation (the most important part)
- First-class identifiers in the API: **`user_id`, `agent_id`, `run_id`** (session). Since mem0 v1.0 the convention was unified: these IDs go as top-level kwargs in `add()`/`delete_all()`, but **inside a `filters` dictionary** in `search()`/`get_all()` ([WebFetch of the migration guide](https://docs.mem0.ai/), confirmed by a filter search).
- **Advanced Metadata Filtering** (`docs.mem0.ai/open-source/features/metadata-filtering`, requires mem0 ≥1.0.0): supports nestable **AND / OR / NOT** logical operators, comparators (`gte`, `lte`, `gt`, `lt`), text matching and list membership (`contains`, `in`). Documented example:
  ```
  client.search("work experience", {
    filters: { AND: [ { user_id: "alice" }, { categories: { contains: "professional_details" } } ] },
    topK: 5, rerank: true
  })
  ```
  ([deepwiki.com/mem0ai/mem0/11.4-metadata-filtering](https://deepwiki.com/mem0ai/mem0/11.4-metadata-filtering)).
- **Custom Categories** (`docs.mem0.ai/features/custom-categories`): default categories (`personal_details`, `family`, `professional_details`, `travel`, `health`, `technology`, etc.) and the ability to define your own, but the Platform-vs-OSS comparison doc marks this feature as **"Limited" in OSS vs "✅" in Platform** ([WebFetch platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss)).
- **Custom Instructions** (`docs.mem0.ai/platform/features/custom-instructions`): they act as an extraction filter/prompt to focus on what gets stored, but it is a global project/API-key setting, not a query-time scoping mechanism.
- **Conclusion on isolation**: mem0 **has no native concept of "context/project/domain" that automatically partitions the search space** the way a first-class namespace would. The closest things are `user_id`/`agent_id`/`run_id` (designed for multi-tenancy and sessions, not for the same user's "life domains") and arbitrary metadata that the application must: (a) design the schema for, (b) tag consistently on every insert, and (c) **remember to apply the filter on every search** — if the app forgets to pass the `project=expense_tracker` vs `domain=finanzas_personales` filter, semantic search mixes both again, exactly the problem that motivates KnowledgeOS. There is no automatic resolution of vocabulary ambiguity between contexts: the engine does not "know" that two contexts share a term and does not re-rank/disambiguate by itself — all the responsibility falls on how the app structures its `filters`.

### 1.5 MCP support
- There is an **official mem0 MCP server** (`mem0ai/mem0-mcp` on GitHub, and the `@mem0/mcp-server` package) that exposes save/search/update/delete memory tools to MCP clients (Claude Desktop, Cursor, etc.) ([github.com/mem0ai/mem0-mcp](https://github.com/mem0ai/mem0-mcp), [pypi.org/project/mem0-mcp-server](https://pypi.org/project/mem0-mcp-server/)).
- Important: the official variant documented at `docs.mem0.ai/platform/mem0-mcp` runs **against the Mem0 cloud account** ("Nothing runs on your machine... memories live in your Mem0 account"), not against a self-hosted server. For self-hosted there are community forks/templates (`coleam00/mcp-mem0`, `odin2-hash/mem0-mcp-server`, `pinkpixel-dev/mem0-mcp`) that do point to your own instance, but they are not maintained by the core team ([github.com/coleam00/mcp-mem0](https://github.com/coleam00/mcp-mem0)).

### 1.6 Lifecycle
- The A.U.D.N. pipeline (see 1.3) handles automatic update/replacement when a new memory contradicts or extends an existing one, and removes obsolete memories via DELETE. This is real supersession, managed by an LLM on every `add()` ([memo.d.foundation/breakdown/mem0](https://memo.d.foundation/breakdown/mem0)).
- **Temporal decay (memory decay) and explicit temporal reasoning are exclusive to Mem0 Platform v3** — they are not in OSS ([docs.mem0.ai/platform/platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss)).
- A community issue/audit reported that of 10,134 audited mem0 entries, 97.8% were "junk" — a sign that the quality of automatic extraction/curation is a practical problem reported by real users ([github.com/mem0ai/mem0/issues/4573](https://github.com/mem0ai/mem0/issues/4573)).

### 1.7 How to run a minimal local benchmark
1. `docker compose up` with the official stack (API + Postgres/pgvector) — see the guide ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)), or `pip install mem0ai` for embedded use in Python.
2. Configure `OPENAI_API_KEY` (or a local LLM via Ollama) for the extraction pipeline.
3. Insert memory: `POST /memories` with body `{"messages":[{"role":"user","content":"..."}], "user_id":"test_user", "metadata":{"project":"expense_tracker"}}`.
4. Search with metadata isolation: `POST /search` with `{"query":"¿cuánto gasté este mes?", "filters":{"AND":[{"user_id":"test_user"},{"metadata":{"project":"personal_finance"}}]}}`.
5. Repeat without the metadata filter to measure how much worse contamination gets between "Expense Tracker" (software project) and "personal finances" (life domain) when the app does not apply the filter — this is exactly the control experiment that validates or refutes KnowledgeOS's hypothesis.

## 2. Zep / Graphiti (getzep/graphiti)

### 2.1 Project status — **the most important finding of this research**
- **Zep Community Edition (the full self-hosted server, "Zep as a service" style) was discontinued.** The official blog "Announcing a New Direction for Zep's Open Source Strategy" confirms: Zep abandoned the open-core model because maintaining two related but distinct products led to design decisions that limited each other, split resources, slower updates and lower community engagement; they also explicitly rejected the typical open-core practice of deliberately limiting features to push people toward the paid product ([blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/)).
- The Zep Community Edition repo **remains under the Apache 2.0 license but with no updates or active support** — the code was moved to a `legacy/` folder ([blog.getzep.com](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/), [github.com/getzep/zep](https://github.com/getzep/zep)). **There is no official "complete self-hosted" successor**: whoever wants to self-host must build their own service layer on top of **Graphiti**, which is the temporal knowledge graph library/engine, not a turnkey memory product.
- Graphiti (the engine) is active and growing (~14K+ stars mentioned in the official blog), **Apache 2.0** license, and is what also powers the commercial Zep Cloud service ([blog.getzep.com/graphiti-knowledge-graphs-falkordb-support](https://blog.getzep.com/graphiti-knowledge-graphs-falkordb-support/), [github.com/getzep/graphiti](https://github.com/getzep/graphiti)).
- **Implication for KnowledgeOS**: the real option of "adopting self-hosted Zep" no longer exists as a complete maintained service. The real option is "build on Graphiti", which is a low-level graph engine (episodes → entities/relations → communities), with no product layers such as authentication, user multi-tenancy, UI, session summaries, etc. — Graphiti is more of an ingredient than a solution.

### 2.2 Self-hosted deployment requirements
- Graphiti requires a graph database: **Neo4j** (≥5.26, primary/historical; free Community Edition) or **FalkorDB** (a graph engine on top of Redis, lighter) or Kuzu/Amazon Neptune as additional options ([help.getzep.com/graphiti/configuration/neo-4-j-configuration](https://help.getzep.com/graphiti/configuration/neo-4-j-configuration), [github.com/getzep/graphiti](https://github.com/getzep/graphiti)).
- FalkorDB is promoted as lighter: "idles far below a comparable Neo4j deployment" and its own benchmarks claim ~6x better memory efficiency than a traditional graph ([falkordb.com/blog/graphiti-falkordb-multi-agent-performance](https://www.falkordb.com/blog/graphiti-falkordb-multi-agent-performance/)). There is also **FalkorDB Lite**, an embedded variant with no server/Docker (file only) — useful for very light local tests ([github.com/getzep/graphiti/issues/1240](https://github.com/getzep/graphiti/issues/1240)).
- LLM required: Graphiti needs an LLM for entity/relation extraction from each episode (by default via the OpenAI API in the official examples; configurable to other providers).
- No official minimum RAM figures were found for the full stack; with FalkorDB instead of Neo4j consumption drops noticeably (Neo4j alone, ~1GB extra according to third parties who documented removing it from the compose) — a 4 vCPU/8GB VPS looks viable with FalkorDB + API + remote LLM, but **there is no official benchmark confirming it**; it would have to be measured empirically as part of Phase 0.

### 2.3 Memory model
- Multi-layer **temporal knowledge graph**: Episodes subgraph (discrete units of information, text or JSON), semantic Entities subgraph, Edges/relations (with `search_memory_facts`, filters by `edge_types`, `center_node_uuid`, date range), and Communities subgraph (clusters of related entities via the Leiden algorithm) ([deepwiki.com/getzep/graphiti/11-examples-and-use-cases](https://deepwiki.com/getzep/graphiti/11-examples-and-use-cases), [help.getzep.com/graphiti/core-concepts/communities](https://help.getzep.com/graphiti/core-concepts/communities)).
- It is **temporally aware**: every fact/relation has validity in time (bi-temporal), which gives native support for supersession (see 2.6). This is the most advanced of the three alternatives in terms of data model.
- It does not use KnowledgeOS's explicit semantic/episodic/procedural taxonomy; its native unit is the "Episode" (temporal event) from which entities and relations are derived — conceptually closer to "episodic memory + extracted facts" than to a four-type taxonomy.

### 2.4 Context isolation — the real strength of this alternative
- **Graph Namespacing via `group_id`**: every node and edge can be associated with a `group_id`; nodes/edges with the same `group_id` form a cohesive and **isolated** graph, queryable independently of other namespaces ([help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)).
- Explicit API:
  ```python
  await graphiti.add_episode(name="...", episode_body="...", source=EpisodeType.text, group_id="customer_team")
  await graphiti.search(query="Wool Runners", group_id="product_catalog")
  ```
  ([help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)).
- If no `group_id` is specified, the server uses `"main"` by default ([Zep docs via WebSearch](https://help.getzep.com/users-and-user-graphs)) — that is, without explicit discipline from the app, everything falls into a single shared namespace (the same risk as mem0 if you don't tag).
- **Cross-namespace search is not automatic**: the documentation explicitly says that to combine results from several `group_id`s you have to "perform multiple queries and combine results in the application logic" ([help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)) — that is, isolation is strong by default (namespaces don't leak into each other by accident) but the intentional merging of contexts is the app's responsibility, not automatic.
- Additionally, Zep/Graphiti models **per-user graphs** (`User Graph`, one per user) and **shared group graphs** (`Group Graphs`) for context shared across users without duplicating data — a more mature pattern than mem0's simple metadata filter ([help.getzep.com/users-and-user-graphs](https://help.getzep.com/users-and-user-graphs), [help.getzep.com/v2/cookbook/how-to-share-memory-across-users-using-group-graphs](https://help.getzep.com/v2/cookbook/how-to-share-memory-across-users-using-group-graphs)).
- **No automatic handling of shared vocabulary ambiguity across distinct namespaces is documented** — isolation is structural (hard partitioning by `group_id`), not semantic/intelligent: two distinct `group_id`s ("expense_tracker_project" and "finanzas_personales") would never mix because they are literally different subgraphs, BUT again it depends 100% on the application creating and using the right `group_id`s consistently. It is the same discipline requirement as mem0, except that here the partitioning is "harder" (isolated subgraphs) instead of "softer" (post-hoc filter over a shared collection), which in theory reduces the risk of leaks.

### 2.5 MCP support
- There is an **official MCP server** in Graphiti's own repo: `getzep/graphiti/mcp_server` ([github.com/getzep/graphiti/blob/main/mcp_server/README.md](https://github.com/getzep/graphiti/blob/main/mcp_server/README.md)).
- It exposes high-level functions via the MCP protocol: episode management, entity management, search capabilities, group (`group_id`) management and graph maintenance. It supports multiple LLM/embeddings providers and multiple graph backends (FalkorDB by default, Neo4j optional), over HTTP or stdio ([docs.falkordb.com/agentic-memory/graphiti-mcp-server.html](https://docs.falkordb.com/agentic-memory/graphiti-mcp-server.html)).
- Easy deployment: combined FalkorDB + MCP server Docker image, `docker compose up` ([docs.falkordb.com/agentic-memory/graphiti-mcp-server.html](https://docs.falkordb.com/agentic-memory/graphiti-mcp-server.html)).
- This is the **most native and "self-hosted-first"** MCP support of the three alternatives, because it lives in the same repo as the open source engine (unlike mem0, whose official MCP points to the cloud).

### 2.6 Lifecycle
- **Native support for temporal supersession**: when potentially conflicting relations are detected as new information arrives, an LLM-based resolver determines whether certain relations must be marked **invalid (invalidated) instead of physically deleted**, preserving the timeline for temporal reasoning — this is precisely the kind of "invalidation/supersession of obsolete memories" that KnowledgeOS's hypothesis asks for, and it is more explicit/structural here than in mem0 or Letta ([memo.d.foundation/breakdown/mem0](https://memo.d.foundation/breakdown/mem0) citing the Zep paper; see also [arxiv.org/html/2501.13956v1](https://arxiv.org/html/2501.13956v1), the paper "Zep: A Temporal Knowledge Graph Architecture for Agent Memory").
- No documentation of automatic "decay" by age was found — temporal management is about the validity of facts (bi-temporal), not progressive forgetting.

### 2.7 How to run a minimal local benchmark
1. `docker compose up` from `getzep/graphiti/mcp_server` (combined FalkorDB + MCP server image) — or install Graphiti directly: `pip install graphiti-core` (or `graphiti-core-falkordb` for FalkorDB extras) ([pypi.org/project/graphiti-core-falkordb](https://pypi.org/project/graphiti-core-falkordb/)).
2. Configure an LLM API key (OpenAI by default in the repo's `quickstart_neo4j.py` / `quickstart_falkordb.py` examples) ([github.com/getzep/graphiti/blob/main/examples/quickstart/README.md](https://github.com/getzep/graphiti/blob/main/examples/quickstart/README.md)).
3. Insert episodes with a namespace: `await graphiti.add_episode(name="expense_note", episode_body="Compré una laptop", source=EpisodeType.text, group_id="expense_tracker_project")` and another with `group_id="finanzas_personales"`.
4. Search with explicit partitioning: `await graphiti.search(query="¿cuánto gasté este mes?", group_id="finanzas_personales")`.
5. Compare against a search without `group_id` (default `"main"` namespace) to quantify how much cross contamination occurs when the app does not partition — same control experiment as in mem0, but here isolation is structural per subgraph instead of a post-filter.

## 3. Letta (letta-ai/letta, formerly MemGPT)

### 3.1 Project status
- Active, it is the direct evolution of the MemGPT research project. **Open source core, Apache 2.0, no license fees** ([theagentsindex.com/letta](https://theagentsindex.com/letta) via search).
- Business model: self-hosting gives unlimited agents and full data control; Letta Cloud offers a free tier (up to 3 managed agents, BYOK, no login for local use), a Pro plan ($20/month, up to 20 agents with a "Letta Auto" model quota + pay-as-you-go), and custom Team/Enterprise plans (June 2026 figures) ([web search, no single official pricing URL confirmed — figure reported by a third-party aggregator](https://theagentsindex.com/letta)).
- The difference between self-hosted and cloud is mainly **managed infrastructure + ADE (Agent Development Environment, the development UI) + managed scaling**, not a hidden layer of memory features — the memory core (blocks, archival, recall, sleep-time) is the same engine in both cases ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker), [rywalker.com/research/letta](https://rywalker.com/research/letta)).

### 3.2 Self-hosted deployment requirements
- A single official Docker container `letta/letta` that packages the Python server + Postgres with **pgvector** ("bundled Postgres"); it can also be pointed at an external Postgres with the pgvector extension via `LETTA_PG_URI` ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker), [docs.letta.com/guides/selfhosting/postgres](https://docs.letta.com/guides/selfhosting/postgres)).
- Startup example:
  ```
  docker run -v ~/.letta/.persist/pgdata:/var/lib/postgresql/data -p 8283:8283 \
    -e OPENAI_API_KEY="..." letta/letta:latest
  ```
  ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker) via search).
- RAM estimated by third-party sources: Python server ~500MB + embedded Postgres ~300MB + a working set of memory blocks/pgvector indexes that grows with use; under load it can exceed 1.5GB, with an active agent generating ~50-200MB/month of DB growth. It is the lightest footprint of the three for a single agent/user, and fits comfortably in a 4 vCPU/8GB VPS next to Postgres — although these figures come from community guides, not from the project's official benchmarks.
- Model-agnostic: works with hosted models (OpenAI, Anthropic, etc.) or self-hosted via vLLM/Ollama.

### 3.3 Memory model
- **Three-tier** architecture, inspired by the computer memory hierarchy:
  - **Core Memory**: labeled text blocks (`label`/`value`), "pinned" in the context window, directly editable by the agent itself through `core_memory_append` / `core_memory_replace` tools. Conventional blocks: `human` (what the agent knows about the user) and `persona` (the agent's self-description); common custom blocks for task/project state ([docs.letta.com/guides/core-concepts/memory/memory-blocks](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)).
  - **Recall Memory**: full conversation history, searchable via `conversation_search` (hybrid text + semantic search, with an ISO 8601 date range filter).
  - **Archival Memory**: long-term vector storage that the agent queries explicitly via `archival_memory_search` (semantic embedding search, with a **filter by `tags`** — `any`/`all` strategy — and a date range) ([API reference search + evidence file](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).
- Backend: Postgres + pgvector, with hybrid vector + full-text search fused by reciprocal rank fusion.
- It does not implement a native semantic/episodic/procedural/decision taxonomy — its model is "core/recall/archival" according to architectural role (active context vs. history vs. external storage), not according to the epistemic type of the memory.
- **Sleep-time agents**: background agents that share memory with the main agent and run between conversations to consolidate fragmented memories, identify patterns, reorganize/deduplicate blocks and archive/prune obsolete information ([docs.letta.com/guides/agents/architectures/sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime/), [letta.com/blog/sleep-time-compute](https://www.letta.com/blog/sleep-time-compute/)).

### 3.4 Context isolation
- Letta's **primary and strongest isolation mechanism is "one agent = one context"**: if you want isolated memory, the documentation's explicit recommendation is to **create separate agents** — each agent has its own core/recall/archival memory state, completely isolated from other agents unless blocks are explicitly shared ([docs.letta.com search on Conversations](https://www.letta.com/blog/conversations/)).
- **Shared Memory Blocks**: several agents can point to the same block; if one agent updates it, all those with it attached see the change immediately. Blocks can be marked read-only for reference data/constant policies. To avoid race conditions when sharing, the recommendation is for each agent to update only its own section using timestamps/agent IDs in the content — that is, **there is no native locking**, it is application discipline ([docs.letta.com/guides/core-concepts/memory/shared-memory](https://docs.letta.com/guides/core-concepts/memory/shared-memory/), [docs.letta.com/tutorials/shared-memory-blocks](https://docs.letta.com/tutorials/shared-memory-blocks/)).
- **Conversations** (newest feature): lets a single agent serve many users/threads in parallel without creating an agent per user, searching across conversations — but the documentation itself clarifies that if real isolation between those threads is needed, the recommendation is still to separate agents; "Conversations" is meant for shared institutional knowledge management, not for separating contradictory domains of the same user ([letta.com/blog/conversations](https://www.letta.com/blog/conversations/)).
- **Tags in Archival Memory**: `archival_memory_search` supports filtering by `tags` (`match_all` or `match_any`), and the agent knows at all times which tags exist in its archive because the list is compiled into the context window — this is a fine-grained scoping mechanism **within a single agent**, analogous to mem0's metadata filter, but limited to the archival memory layer (it does not apply to core memory or recall memory) ([evidence file / API reference search](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).
- **There is no native concept of "project" or "domain" at the platform level that automatically partitions search within a single agent** beyond manual tags in archival memory. For the KnowledgeOS scenario (same user, two domains that share vocabulary), Letta offers two paths, neither "free": (a) create a different agent per domain — perfect isolation but it loses the notion of "a single personal assistant" and complicates legitimately sharing cross context, or (b) a single agent with archival memory tags — it requires the same manual tagging discipline as mem0, and does not cover core/recall memory.
- No automatic handling of vocabulary ambiguity between blocks or tags is documented: it is the application's responsibility to decide the partitioning.

### 3.5 MCP support
- Letta **does have native, official MCP integration as a client**: "Letta acts as the host, creating clients that connect to external servers" — the agent can consume tools/resources from external MCP servers via the standard protocol ([docs.letta.com/guides/mcp/overview](https://docs.letta.com/guides/mcp/overview/)).
- This is different from what is typically sought ("does it have an MCP server that exposes Letta's memory to other clients?") — for that case only **unofficial community implementations** were found (`oculairmedia/Letta-MCP-server` in Rust, `@iflow-mcp/letta-mcp-server` on npm), not an MCP server maintained by the core team that exposes Letta's memory outward ([github.com/oculairmedia/Letta-MCP-server](https://github.com/oculairmedia/Letta-MCP-server)).

### 3.6 Lifecycle
- **Sleep-time agents** are the consolidation/cleanup mechanism: they identify patterns, reorganize and deduplicate blocks, and archive/prune obsolete information in the background ([docs.letta.com/guides/agents/architectures/sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime/)).
- There is an open issue asking for **"Archival Memory Deduplication and Consolidation"** as a feature — a sign that as of August 2026 automatic deduplication/consolidation of archival memory is still an area under active development, not a mature, guaranteed out-of-the-box feature ([github.com/letta-ai/letta/issues/3116](https://github.com/letta-ai/letta/issues/3116)).
- All state (including memory blocks) is versioned via a git-like system ("MemFS"), giving version history and date-range filtering across all layers — it is the only one of the three with source-control-style versioning for memory ([evidence file](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).
- Weaknesses documented by third-party comparison: no structured graph-like extraction of entities/relations, no conflict detection between contradictory memories, no "why"/provenance metadata for a memory, and direct memory editing (replace/append) without a formal semantic version chain ([github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).

### 3.7 How to run a minimal local benchmark
1. `docker run -v ~/.letta/.persist/pgdata:/var/lib/postgresql/data -p 8283:8283 -e OPENAI_API_KEY="..." letta/letta:latest` (Postgres + pgvector come embedded) ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker)).
2. `pip install letta-client` for the Python SDK.
3. Create two test agents (one per domain) **or** one agent with separate blocks/tags:
   ```python
   from letta_client import Letta
   client = Letta(base_url="http://localhost:8283")
   agent = client.agents.create(
       model="openai/gpt-4o-mini",
       embedding="openai/text-embedding-3-small",
       memory_blocks=[{"label": "human", "value": "..."}]
   )
   ```
4. Insert into archival memory with tags: `client.agents.passages.create(agent_id=..., text="Compré una laptop para el proyecto", tags=["expense_tracker"])` and another with `tags=["finanzas_personales"]`.
5. Search with `archival_memory_search(query="¿cuánto gasté este mes?", tags=["finanzas_personales"], tag_match_mode="all")` vs. without tags, to measure cross contamination when the app does not filter explicitly — and also compare against the "two separate agents" scenario to see the cost of perfect isolation vs. single-agent with tags.

## 5. Preliminary verdict per alternative

**mem0 — does NOT solve context isolation natively.**
It only offers general-purpose metadata filters (`user_id`/`agent_id`/`run_id` + AND/OR/NOT over arbitrary metadata) that the application must design, populate and apply consistently on every insert and search. There is no "project/domain" concept that partitions by default; if the app forgets the filter, mem0 mixes everything — the same failure that motivates KnowledgeOS. In addition, the removal of graph memory from OSS in 2026 (confirmed in [PR #4805 / issue #6591](https://github.com/mem0ai/mem0/issues/6591)) further reduces its ability to model relations between contexts. Evidence: [docs.mem0.ai/platform/platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss), [deepwiki.com/mem0ai/mem0/11.4-metadata-filtering](https://deepwiki.com/mem0ai/mem0/11.4-metadata-filtering), [GitHub Discussion #3112](https://github.com/mem0ai/mem0/discussions/3112).

**Zep/Graphiti — solves context isolation PARTIALLY, and is the strongest technical proposal of the three, but with a serious organizational caveat.**
Graphiti's `group_id` gives real structural partitioning (genuinely isolated subgraphs, not just a post-hoc filter), which mitigates cross contamination better than a flat metadata filter — and it comes with native temporal supersession, the most mature lifecycle of the three. But **there is no automatic ambiguity resolution between namespaces** (the partition is hard, not "intelligent"), intentionally combining contexts requires application logic, and above all: **there is no maintained "self-hosted Zep" product** — only the Graphiti engine, which forces you to build the service layer, multi-tenancy and UI from scratch. That is, it solves the technical isolation problem better than the other two, but as an "alternative to adopt" it is really "an engine to build on", not very different in engineering effort from building from scratch with a temporal graph already solved as the foundation. Evidence: [help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing), [blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/).

**Letta — solves context isolation PARTIALLY, with a different pattern (per-agent isolation, not data namespace).**
The robust path is "one agent per domain", which gives perfect isolation but sacrifices the idea of a single personal assistant with a complete view of the user (precisely what KnowledgeOS probably wants: a single brain with internal partitions, not disconnected agents). The fine path (`tags` in archival memory) is manual, similar in maturity to mem0's metadata filter, and does not cover core memory or recall memory. There is no "project" concept at the platform level. In its favor: git-like versioning of all memory and sleep-time agents give a decent lifecycle, although automatic deduplication is still an open feature request ([issue #3116](https://github.com/letta-ai/letta/issues/3116)). Evidence: [docs.letta.com/guides/core-concepts/memory/shared-memory](https://docs.letta.com/guides/core-concepts/memory/shared-memory/), [letta.com/blog/conversations](https://www.letta.com/blog/conversations/).

### General conclusion for the Phase 0 decision
None of the three alternatives solves cross-context contamination in a **native and automatic** way (none detects or disambiguates vocabulary shared between domains unless the application designs and applies the partitioning). The difference between them is the **quality of the manual partitioning mechanism** they offer: mem0 gives a soft metadata filter over a shared collection; Letta gives strong isolation but at the level of a whole agent (coarse grain) plus fine tags only in archival memory; Graphiti gives the cleanest structural partitioning (truly isolated subgraphs via `group_id`) but as a low-level engine without a complete memory product around it, and with the added complication that Zep's ready-to-use "self-hosted" offering as such no longer exists. If KnowledgeOS wants context isolation as a central differentiator, **building that partitioning layer in-house (possibly using Graphiti as the underlying graph engine instead of starting from scratch at the graph layer) seems more aligned with the project's hypothesis than adopting mem0 or Letta as they are**, since neither was designed around "life domains that share vocabulary" as a first-class problem.
