# Fase 0 — Investigación de alternativas a construir desde cero (KnowledgeOS)

Fecha de investigación: 2026-08-06
Alcance: evaluar si **mem0**, **Zep/Graphiti** o **Letta** ya resuelven el problema central de KnowledgeOS — la **contaminación entre contextos** en la recuperación de memoria personal (ej. "Expense Tracker" el proyecto de software vs. "finanzas personales" el dominio de vida, que comparten vocabulario y confunden a un buscador semántico plano).

> Metodología: búsqueda web y lectura de documentación oficial, repos de GitHub, issues/discussions y blogs técnicos de terceros, a fecha de agosto de 2026. Todas las afirmaciones llevan URL de referencia. Donde la documentación es ambigua o contradictoria (pasó con mem0 y con Zep) se señala explícitamente y se cita la fuente más autorizada (repo/PR/issue oficial).

---

## 1. mem0 (mem0ai/mem0)

### 1.1 Estado del proyecto
- Muy activo, ~48K+ estrellas en GitHub, licencia **Apache 2.0** para el SDK/servidor open source ([LICENSE](https://github.com/mem0ai/mem0/blob/main/LICENSE), [repo](https://github.com/mem0ai/mem0)).
- Modelo de negocio "open-core": SDK/servidor OSS gratuito + **Mem0 Platform** (cloud, con planes de pago y free tier de 10K memorias/mes) ([atlan.com](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/)).
- **Hallazgo crítico**: en 2026, mem0 **eliminó por completo la Graph Memory del SDK open source** (PR #4805, "port v3 pipeline with hybrid search, entity extraction, and additive scoring"). Se borraron los directorios `mem0/graphs/`, el soporte a Neo4j/Memgraph como graph store, y las opciones de config `enable_graph`/`graph_store`. Un issue de julio 2026 (#6591) confirma que incluso la documentación interna (`AGENTS.md`) seguía referenciando graph memory como si existiera, cuando ya no existe en el código ([issue #6591](https://github.com/mem0ai/mem0/issues/6591)). Esto contradice guías de terceros y posts de blog más antiguos (incluido el propio blog oficial de self-hosting con Docker) que todavía muestran un contenedor Neo4j como parte del stack — evidencia de que la documentación de mem0 está desactualizada/inconsistente entre sí ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)).
- La página oficial de comparación Platform vs OSS (`docs.mem0.ai/platform/platform-vs-oss`) todavía lista "Graph memory: ✅ Built-in (Platform) / ✅ External graph store (OSS)", lo cual está en conflicto directo con el PR de eliminación — es decir, **la propia documentación de mem0 se contradice a sí misma en agosto de 2026**. La fuente más confiable es el código fuente y el issue de seguimiento, que confirman remoción total en OSS.
- La versión self-hosted **no está completa** frente a cloud: faltan autenticación/login, decaimiento de memoria (v3), razonamiento temporal (v3), webhooks, exportación, dashboard, analítica, auto-scaling y alta disponibilidad — todo eso es exclusivo de Platform ([docs.mem0.ai/platform/platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss) vía WebFetch; confirmado indirectamente en [GitHub Discussion #3112](https://github.com/mem0ai/mem0/discussions/3112)).

### 1.2 Requisitos de despliegue self-hosted
- Stack Docker oficial (guía de blog): 3 contenedores — API FastAPI, **Postgres + pgvector** (vector store por defecto) y (históricamente) Neo4j para grafo — pero el grafo ya no aplica a OSS, así que el stack real mínimo hoy es **API + Postgres/pgvector** ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)).
- LLM requerido para extracción de hechos: por defecto OpenAI (`gpt-5-nano` para extracción, `text-embedding-3-small` para embeddings), con alternativa local vía Ollama (`llama3.1`) para operar offline ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)).
- RAM: la misma guía indica que una instancia t3.medium (2 vCPU / 4 GB RAM) es el mínimo viable corriendo Neo4j + pgvector + API juntos; para carga real recomiendan t3.large (8 GB). Sin Neo4j (ya no necesario en OSS), el footprint baja considerablemente — se estima cómodo en un VPS de 4 vCPU/8GB junto a Postgres, especialmente si el LLM de extracción es remoto (API) y no local.
- Soporta 20+ vector stores (Qdrant, Chroma, Milvus, Pinecone, pgvector, etc.), lo que da flexibilidad de infraestructura ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)). Existen reportes de fricción real: pin de versión de Qdrant desactualizado (mem0 pedía 1.13.0 mientras Qdrant iba en 1.17.0), auto-recall descartando memorias silenciosamente, embeddings ignorando `baseURL` configurado, y SDKs de proveedores faltantes que rompen el arranque ([atlan.com](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/), [GitHub Discussion #3112](https://github.com/mem0ai/mem0/discussions/3112)).

### 1.3 Modelo de memoria
- Colección **vectorial** (Postgres/pgvector, Qdrant, etc.) como estructura central. El grafo ya no existe en OSS (ver 1.1).
- Pipeline de extracción con LLM que produce "memory candidates" y les aplica una de cuatro operaciones — **A.U.D.N.: ADD, UPDATE, DELETE, NONE** — comparando cada hecho nuevo contra memorias semánticamente similares existentes ([memo.d.foundation/breakdown/mem0](https://memo.d.foundation/breakdown/mem0), [arxiv.org/html/2504.19413v1](https://arxiv.org/html/2504.19413v1)).
- Documentación de terceros describe sub-tipos conceptuales — memoria episódica (resumen de interacciones), semántica (hechos/preferencias) y procedural (flujos de trabajo) — pero esto es una capa de interpretación externa, no un tipo de dato explícito y primario del schema de mem0 ([47billion.com](https://47billion.com/blog/ai-agent-memory-types-implementation-best-practices/), [digitalapplied.com](https://www.digitalapplied.com/blog/agent-memory-architectures-vector-graph-episodic)). El grafo (cuando existía) sí tenía tipado de entidades (Person, Location, Event, etc.) pero eso ya no aplica a OSS.

### 1.4 Aislamiento de contexto (lo más importante)
- Identificadores de primera clase en la API: **`user_id`, `agent_id`, `run_id`** (sesión). Desde mem0 v1.0, la convención unificó: estos IDs van como kwargs top-level en `add()`/`delete_all()`, pero **dentro de un diccionario `filters`** en `search()`/`get_all()` ([WebFetch de guía de migración](https://docs.mem0.ai/), confirmado por búsqueda de filtros).
- **Metadata Filtering avanzado** (`docs.mem0.ai/open-source/features/metadata-filtering`, requiere mem0 ≥1.0.0): soporta operadores lógicos **AND / OR / NOT** anidables, comparadores (`gte`, `lte`, `gt`, `lt`), coincidencia de texto y pertenencia a listas (`contains`, `in`). Ejemplo documentado:
  ```
  client.search("work experience", {
    filters: { AND: [ { user_id: "alice" }, { categories: { contains: "professional_details" } } ] },
    topK: 5, rerank: true
  })
  ```
  ([deepwiki.com/mem0ai/mem0/11.4-metadata-filtering](https://deepwiki.com/mem0ai/mem0/11.4-metadata-filtering)).
- **Custom Categories** (`docs.mem0.ai/features/custom-categories`): categorías por defecto (`personal_details`, `family`, `professional_details`, `travel`, `health`, `technology`, etc.) y la posibilidad de definir categorías propias, pero la doc de comparación Platform-vs-OSS marca esta feature como **"Limited" en OSS vs "✅" en Platform** ([WebFetch platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss)).
- **Custom Instructions** (`docs.mem0.ai/platform/features/custom-instructions`): actúan como filtro/prompt de extracción para enfocar qué se guarda, pero es una configuración global del proyecto/API-key, no un mecanismo de scoping en tiempo de consulta.
- **Conclusión sobre aislamiento**: mem0 **no tiene un concepto nativo de "contexto/proyecto/dominio" que particione automáticamente el espacio de búsqueda** como haría un namespace de primera clase. Lo más cercano es `user_id`/`agent_id`/`run_id` (pensados para multi-tenancy y sesiones, no para "dominios de vida" del mismo usuario) y metadata arbitraria que la aplicación debe: (a) decidir el esquema, (b) etiquetar consistentemente cada memoria al insertar, y (c) **recordar aplicar el filtro en cada búsqueda** — si la app olvida pasar el filtro `project=expense_tracker` vs `domain=finanzas_personales`, la búsqueda semántica vuelve a mezclar ambos, exactamente el problema que motiva KnowledgeOS. No hay resolución automática de ambigüedad de vocabulario entre contextos: el motor no "sabe" que dos contextos comparten término y no reordena/desambigua por sí mismo — toda la responsabilidad recae en cómo la app estructura sus `filters`.

### 1.5 Soporte MCP
- Existe un **servidor MCP oficial de mem0** (`mem0ai/mem0-mcp` en GitHub, y paquete `@mem0/mcp-server`) que expone herramientas de guardar/buscar/actualizar/borrar memoria a clientes MCP (Claude Desktop, Cursor, etc.) ([github.com/mem0ai/mem0-mcp](https://github.com/mem0ai/mem0-mcp), [pypi.org/project/mem0-mcp-server](https://pypi.org/project/mem0-mcp-server/)).
- Importante: la variante oficial documentada en `docs.mem0.ai/platform/mem0-mcp` corre **contra la cuenta cloud de Mem0** ("Nothing runs on your machine... memories live in your Mem0 account"), no contra un servidor self-hosted. Para self-hosted existen forks/plantillas de la comunidad (`coleam00/mcp-mem0`, `odin2-hash/mem0-mcp-server`, `pinkpixel-dev/mem0-mcp`) que sí apuntan a una instancia propia, pero no son mantenidos por el equipo core ([github.com/coleam00/mcp-mem0](https://github.com/coleam00/mcp-mem0)).

### 1.6 Ciclo de vida
- El pipeline A.U.D.N. (ver 1.3) maneja actualización/reemplazo automático cuando una memoria nueva contradice o amplía una existente, y elimina memorias obsoletas vía DELETE. Esto es supersedencia real, gestionada por un LLM en cada `add()` ([memo.d.foundation/breakdown/mem0](https://memo.d.foundation/breakdown/mem0)).
- **Decaimiento temporal (memory decay) y razonamiento temporal explícito son exclusivos de Mem0 Platform v3** — no están en OSS ([docs.mem0.ai/platform/platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss)).
- Un issue/auditoría comunitaria reportó que de 10,134 entradas de mem0 auditadas, 97.8% eran "junk" — señal de que la calidad de la extracción/curación automática es un problema práctico reportado por usuarios reales ([github.com/mem0ai/mem0/issues/4573](https://github.com/mem0ai/mem0/issues/4573)).

### 1.7 Cómo correr un benchmark local mínimo
1. `docker compose up` con el stack oficial (API + Postgres/pgvector) — ver guía ([mem0.ai/blog/self-host-mem0-docker](https://mem0.ai/blog/self-host-mem0-docker)), o `pip install mem0ai` para uso embebido en Python.
2. Configurar `OPENAI_API_KEY` (o LLM local vía Ollama) para el pipeline de extracción.
3. Insertar memoria: `POST /memories` con body `{"messages":[{"role":"user","content":"..."}], "user_id":"test_user", "metadata":{"project":"expense_tracker"}}`.
4. Buscar con aislamiento por metadata: `POST /search` con `{"query":"¿cuánto gasté este mes?", "filters":{"AND":[{"user_id":"test_user"},{"metadata":{"project":"personal_finance"}}]}}`.
5. Repetir sin el filtro de metadata para medir cuánto empeora la contaminación entre "Expense Tracker" (proyecto software) y "finanzas personales" (dominio de vida) cuando la app no aplica el filtro — este es exactamente el experimento de control que valida o refuta la hipótesis de KnowledgeOS.

## 2. Zep / Graphiti (getzep/graphiti)

### 2.1 Estado del proyecto — **hallazgo más importante de esta investigación**
- **Zep Community Edition (el servidor self-hosted completo, tipo "Zep as a service") fue descontinuado.** El blog oficial "Announcing a New Direction for Zep's Open Source Strategy" confirma: Zep abandonó el modelo open-core porque mantener dos productos relacionados pero distintos generaba decisiones de diseño que se limitaban mutuamente, recursos repartidos, actualizaciones más lentas y menor engagement de comunidad; además rechazaron explícitamente la práctica típica de open-core de limitar funciones a propósito para empujar hacia el producto de pago ([blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/)).
- El repo de Zep Community Edition **permanece bajo licencia Apache 2.0 pero sin actualizaciones ni soporte activo** — el código se movió a una carpeta `legacy/` ([blog.getzep.com](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/), [github.com/getzep/zep](https://github.com/getzep/zep)). **No hay un sucesor oficial "self-hosted completo"**: quien quiera self-host debe construir su propia capa de servicio sobre **Graphiti**, que es la librería/motor de grafos de conocimiento temporal, no un producto de memoria llave-en-mano.
- Graphiti (el motor) sí está activo y creciendo (~14K+ estrellas mencionadas en blog oficial), licencia **Apache 2.0**, y es lo que además alimenta el servicio comercial Zep Cloud ([blog.getzep.com/graphiti-knowledge-graphs-falkordb-support](https://blog.getzep.com/graphiti-knowledge-graphs-falkordb-support/), [github.com/getzep/graphiti](https://github.com/getzep/graphiti)).
- **Implicación para KnowledgeOS**: la opción real de "adoptar Zep self-hosted" ya no existe como servicio completo mantenido. La opción real es "construir sobre Graphiti", que es un motor de grafo de bajo nivel (episodios → entidades/relaciones → comunidades), sin capas de producto como autenticación, multi-tenant de usuarios, UI, resúmenes de sesión, etc. — Graphiti es más un ingrediente que una solución.

### 2.2 Requisitos de despliegue self-hosted
- Graphiti requiere una base de datos de grafo: **Neo4j** (≥5.26, primaria/histórica; Community Edition gratis) o **FalkorDB** (motor de grafo sobre Redis, más liviano) o Kuzu/Amazon Neptune como opciones adicionales ([help.getzep.com/graphiti/configuration/neo-4-j-configuration](https://help.getzep.com/graphiti/configuration/neo-4-j-configuration), [github.com/getzep/graphiti](https://github.com/getzep/graphiti)).
- FalkorDB se promociona como más liviano: "idles far below a comparable Neo4j deployment" y benchmarks propios reclaman ~6x mejor eficiencia de memoria que grafo tradicional ([falkordb.com/blog/graphiti-falkordb-multi-agent-performance](https://www.falkordb.com/blog/graphiti-falkordb-multi-agent-performance/)). Existe además **FalkorDB Lite**, variante embebida sin servidor/Docker (solo archivo) — útil para pruebas locales muy ligeras ([github.com/getzep/graphiti/issues/1240](https://github.com/getzep/graphiti/issues/1240)).
- LLM requerido: Graphiti necesita un LLM para extracción de entidades/relaciones desde cada episodio (por defecto vía API de OpenAI en los ejemplos oficiales; es configurable a otros proveedores).
- No se encontraron cifras oficiales de RAM mínimas para el stack completo; con FalkorDB en lugar de Neo4j el consumo baja sensiblemente (Neo4j solo, ~1GB extra según terceros que documentaron quitarlo del compose) — un VPS de 4 vCPU/8GB parece viable con FalkorDB + API + LLM remoto, pero **no hay benchmark oficial que lo confirme**; habría que medirlo empíricamente como parte de la Fase 0.

### 2.3 Modelo de memoria
- **Grafo de conocimiento temporal** en múltiples capas: subgrafo de Episodios (unidades discretas de información, texto o JSON), subgrafo de Entidades semánticas, Edges/relaciones (con `search_memory_facts`, filtros por `edge_types`, `center_node_uuid`, rango de fechas), y subgrafo de Comunidades (clusters de entidades relacionadas vía algoritmo de Leiden) ([deepwiki.com/getzep/graphiti/11-examples-and-use-cases](https://deepwiki.com/getzep/graphiti/11-examples-and-use-cases), [help.getzep.com/graphiti/core-concepts/communities](https://help.getzep.com/graphiti/core-concepts/communities)).
- Es **temporalmente consciente**: cada hecho/relación tiene validez en el tiempo (bi-temporal), lo que da soporte nativo a supersedencia (ver 2.6). Esto es lo más avanzado de las tres alternativas en cuanto a modelo de datos.
- No usa la taxonomía semántica/episódica/procedural explícita de KnowledgeOS; su unidad nativa es el "Episode" (evento temporal) del cual se derivan entidades y relaciones — conceptualmente más cercano a "memoria episódica + hechos extraídos" que a una taxonomía de cuatro tipos.

### 2.4 Aislamiento de contexto — el punto fuerte real de esta alternativa
- **Graph Namespacing vía `group_id`**: cada nodo y edge puede asociarse a un `group_id`; nodos/edges con el mismo `group_id` forman un grafo cohesivo e **aislado**, consultable independientemente de otros namespaces ([help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)).
- API explícita:
  ```python
  await graphiti.add_episode(name="...", episode_body="...", source=EpisodeType.text, group_id="customer_team")
  await graphiti.search(query="Wool Runners", group_id="product_catalog")
  ```
  ([help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)).
- Si no se especifica `group_id`, el servidor usa `"main"` por defecto ([Zep docs vía WebSearch](https://help.getzep.com/users-and-user-graphs)) — es decir, sin disciplina explícita de la app, todo cae en un único namespace compartido (mismo riesgo que mem0 si no se etiqueta).
- **La búsqueda cruzada de namespaces no es automática**: la documentación indica explícitamente que para combinar resultados de varios `group_id` hay que "realizar múltiples queries y combinar resultados en la lógica de la aplicación" ([help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)) — es decir, el aislamiento es fuerte por defecto (namespaces no se filtran entre sí accidentalmente) pero la fusión intencional de contextos es responsabilidad de la app, no automática.
- Adicionalmente, Zep/Graphiti modela **grafos por usuario** (`User Graph`, uno por usuario) y **grafos de grupo compartidos** (`Group Graphs`) para contexto compartido entre usuarios sin duplicar datos — un patrón más maduro que el simple filtro de metadata de mem0 ([help.getzep.com/users-and-user-graphs](https://help.getzep.com/users-and-user-graphs), [help.getzep.com/v2/cookbook/how-to-share-memory-across-users-using-group-graphs](https://help.getzep.com/v2/cookbook/how-to-share-memory-across-users-using-group-graphs)).
- **No se documenta manejo automático de ambigüedad de vocabulario compartido entre namespaces distintos** — el aislamiento es estructural (particionamiento duro por `group_id`), no semántico/inteligente: dos `group_id` distintos ("expense_tracker_project" y "finanzas_personales") nunca se mezclarían porque literalmente son subgrafos distintos, PERO de nuevo depende 100% de que la aplicación cree y use los `group_id` correctos consistentemente. Es el mismo requisito de disciplina que mem0, salvo que aquí el particionamiento es más "duro" (subgrafos aislados) en lugar de "blando" (filtro post-hoc sobre una colección compartida), lo cual en teoría reduce el riesgo de fuga.

### 2.5 Soporte MCP
- Existe un **servidor MCP oficial** en el propio repo de Graphiti: `getzep/graphiti/mcp_server` ([github.com/getzep/graphiti/blob/main/mcp_server/README.md](https://github.com/getzep/graphiti/blob/main/mcp_server/README.md)).
- Expone funciones de alto nivel vía protocolo MCP: gestión de episodios, gestión de entidades, capacidades de búsqueda, gestión de grupos (`group_id`) y mantenimiento de grafo. Soporta múltiples proveedores de LLM/embeddings y múltiples backends de grafo (FalkorDB por defecto, Neo4j opcional), sobre HTTP o stdio ([docs.falkordb.com/agentic-memory/graphiti-mcp-server.html](https://docs.falkordb.com/agentic-memory/graphiti-mcp-server.html)).
- Despliegue fácil: imagen Docker combinada FalkorDB + servidor MCP, `docker compose up` ([docs.falkordb.com/agentic-memory/graphiti-mcp-server.html](https://docs.falkordb.com/agentic-memory/graphiti-mcp-server.html)).
- Este es el soporte MCP **más nativo y "self-hosted-first"** de las tres alternativas, porque vive en el mismo repo del motor open source (a diferencia de mem0, cuyo MCP oficial apunta al cloud).

### 2.6 Ciclo de vida
- Soporte **nativo a supersedencia temporal**: al detectar relaciones potencialmente conflictivas cuando llega información nueva, un resolvedor basado en LLM determina si ciertas relaciones deben marcarse como **inválidas (invalidadas) en vez de borrarse físicamente**, preservando la línea de tiempo para razonamiento temporal — esto es justo el tipo de "invalidación/supersedencia de memorias obsoletas" que pide la hipótesis de KnowledgeOS, y es más explícito/estructural aquí que en mem0 o Letta ([memo.d.foundation/breakdown/mem0](https://memo.d.foundation/breakdown/mem0) citando el paper de Zep; ver también [arxiv.org/html/2501.13956v1](https://arxiv.org/html/2501.13956v1), el paper "Zep: A Temporal Knowledge Graph Architecture for Agent Memory").
- No se encontró documentación de "decaimiento" (decay) automático por antigüedad — la gestión temporal es de validez de hechos (bi-temporal), no de olvido progresivo.

### 2.7 Cómo correr un benchmark local mínimo
1. `docker compose up` desde `getzep/graphiti/mcp_server` (imagen combinada FalkorDB + MCP server) — o instalar Graphiti directo: `pip install graphiti-core` (o `graphiti-core-falkordb` para extras de FalkorDB) ([pypi.org/project/graphiti-core-falkordb](https://pypi.org/project/graphiti-core-falkordb/)).
2. Configurar API key de LLM (OpenAI por defecto en los ejemplos `quickstart_neo4j.py` / `quickstart_falkordb.py` del repo) ([github.com/getzep/graphiti/blob/main/examples/quickstart/README.md](https://github.com/getzep/graphiti/blob/main/examples/quickstart/README.md)).
3. Insertar episodios con namespace: `await graphiti.add_episode(name="expense_note", episode_body="Compré una laptop", source=EpisodeType.text, group_id="expense_tracker_project")` y otro con `group_id="finanzas_personales"`.
4. Buscar con partición explícita: `await graphiti.search(query="¿cuánto gasté este mes?", group_id="finanzas_personales")`.
5. Comparar contra una búsqueda sin `group_id` (namespace `"main"` por defecto) para cuantificar cuánta contaminación cruzada ocurre cuando la app no particiona — mismo experimento de control que en mem0, pero aquí el aislamiento es estructural por subgrafo en vez de post-filtro.

## 3. Letta (letta-ai/letta, antes MemGPT)

### 3.1 Estado del proyecto
- Activo, es la evolución directa del proyecto de investigación MemGPT. Núcleo **open source, Apache 2.0, sin fees de licencia** ([theagentsindex.com/letta](https://theagentsindex.com/letta) vía búsqueda).
- Modelo de negocio: self-hosting da agentes ilimitados y control total de datos; Letta Cloud ofrece free tier (hasta 3 agentes gestionados, BYOK, sin login para uso local), plan Pro ($20/mes, hasta 20 agentes con cuota de modelo "Letta Auto" + pay-as-you-go), y planes Team/Enterprise a medida (cifras de junio 2026) ([búsqueda web, sin URL única de precios oficiales confirmada — cifra reportada por agregador de terceros](https://theagentsindex.com/letta)).
- La diferencia entre self-hosted y cloud es principalmente **infraestructura gestionada + ADE (Agent Development Environment, la UI de desarrollo) + escalado gestionado**, no una capa oculta de features de memoria — el core de memoria (bloques, archival, recall, sleep-time) es el mismo motor en ambos casos ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker), [rywalker.com/research/letta](https://rywalker.com/research/letta)).

### 3.2 Requisitos de despliegue self-hosted
- Un único contenedor Docker oficial `letta/letta` que empaqueta el servidor Python + Postgres con **pgvector** ("bundled Postgres"); también se puede apuntar a un Postgres externo con la extensión pgvector vía `LETTA_PG_URI` ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker), [docs.letta.com/guides/selfhosting/postgres](https://docs.letta.com/guides/selfhosting/postgres)).
- Ejemplo de arranque:
  ```
  docker run -v ~/.letta/.persist/pgdata:/var/lib/postgresql/data -p 8283:8283 \
    -e OPENAI_API_KEY="..." letta/letta:latest
  ```
  ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker) vía búsqueda).
- RAM estimada por fuentes de terceros: servidor Python ~500MB + Postgres embebido ~300MB + working set de bloques de memoria/índices pgvector que crece con el uso; bajo carga puede pasar de 1.5GB, con un agente activo generando ~50-200MB/mes de crecimiento en BD. Es la huella más liviana de las tres para un solo agente/usuario, y cabe cómodo en un VPS de 4 vCPU/8GB junto a Postgres — aunque estas cifras provienen de guías comunitarias, no de benchmarks oficiales del proyecto.
- Modelo-agnóstico: funciona con modelos hosted (OpenAI, Anthropic, etc.) o self-hosted vía vLLM/Ollama.

### 3.3 Modelo de memoria
- Arquitectura de **tres niveles**, inspirada en jerarquía de memoria de computadoras:
  - **Core Memory**: bloques de texto etiquetados (`label`/`value`), fijados ("pinned") en la ventana de contexto, editables directamente por el propio agente mediante herramientas `core_memory_append` / `core_memory_replace`. Bloques convencionales: `human` (lo que el agente sabe del usuario) y `persona` (auto-descripción del agente); bloques custom comunes para estado de tarea/proyecto ([docs.letta.com/guides/core-concepts/memory/memory-blocks](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)).
  - **Recall Memory**: historial completo de conversación, buscable vía `conversation_search` (búsqueda híbrida texto + semántica, con filtro de rango de fechas ISO 8601).
  - **Archival Memory**: almacenamiento vectorial de largo plazo que el agente consulta explícitamente vía `archival_memory_search` (búsqueda semántica por embeddings, con **filtro por `tags`** — estrategia `any`/`all` — y rango de fechas) ([búsqueda de referencia API + evidence file](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).
- Backend: Postgres + pgvector, con búsqueda híbrida vector + texto completo fusionada por reciprocal rank fusion.
- No implementa una taxonomía nativa semántica/episódica/procedural/decisión — su modelo es "core/recall/archival" según el rol arquitectónico (contexto activo vs. historial vs. almacenamiento externo), no según tipo epistémico de la memoria.
- **Sleep-time agents**: agentes en segundo plano que comparten memoria con el agente principal y corren entre conversaciones para consolidar memorias fragmentadas, identificar patrones, reorganizar/deduplicar bloques y archivar/podar información obsoleta ([docs.letta.com/guides/agents/architectures/sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime/), [letta.com/blog/sleep-time-compute](https://www.letta.com/blog/sleep-time-compute/)).

### 3.4 Aislamiento de contexto
- El mecanismo de aislamiento **primario y más fuerte de Letta es "un agente = un contexto"**: si se quiere memoria aislada, la recomendación explícita de la documentación es **crear agentes separados** — cada agente tiene su propio estado de core/recall/archival memory, completamente aislado de otros agentes salvo que se compartan bloques explícitamente ([búsqueda de docs.letta.com sobre Conversations](https://www.letta.com/blog/conversations/)).
- **Shared Memory Blocks**: varios agentes pueden apuntar al mismo bloque; si un agente lo actualiza, todos los que lo tienen adjunto ven el cambio de inmediato. Los bloques se pueden marcar de solo lectura para datos de referencia/políticas constantes. Para evitar condiciones de carrera al compartir, la recomendación es que cada agente actualice solo su propia sección usando timestamps/IDs de agente en el contenido — es decir, **no hay locking nativo**, es disciplina de aplicación ([docs.letta.com/guides/core-concepts/memory/shared-memory](https://docs.letta.com/guides/core-concepts/memory/shared-memory/), [docs.letta.com/tutorials/shared-memory-blocks](https://docs.letta.com/tutorials/shared-memory-blocks/)).
- **Conversations** (feature más reciente): permite que un único agente sirva a muchos usuarios/hilos en paralelo sin crear un agente por usuario, buscando across conversaciones — pero la propia documentación aclara que si se necesita aislamiento real entre esos hilos, la recomendación sigue siendo separar agentes; "Conversations" está pensado para gestión de conocimiento institucional compartido, no para separar dominios contradictorios del mismo usuario ([letta.com/blog/conversations](https://www.letta.com/blog/conversations/)).
- **Tags en Archival Memory**: `archival_memory_search` soporta filtrar por `tags` (`match_all` o `match_any`), y el agente conoce en todo momento qué tags existen en su archivo porque la lista se compila en la ventana de contexto — esto es un mecanismo de scoping fino **dentro de un mismo agente**, análogo al filtro de metadata de mem0, pero limitado a la capa de archival memory (no aplica a core memory ni recall memory) ([evidence file / búsqueda API reference](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).
- **No hay concepto nativo de "proyecto" o "dominio" a nivel de plataforma que particione automáticamente la búsqueda dentro de un mismo agente** más allá de tags manuales en archival memory. Para el escenario de KnowledgeOS (mismo usuario, dos dominios que comparten vocabulario), Letta ofrece dos caminos, ninguno "gratis": (a) crear un agente distinto por dominio — aislamiento perfecto pero pierde la noción de "un único asistente personal" y complica compartir contexto legítimamente cruzado, o (b) un solo agente con tags de archival memory — requiere la misma disciplina manual de etiquetado que mem0, y no cubre core/recall memory.
- No se documenta manejo automático de ambigüedad de vocabulario entre bloques o tags: es responsabilidad de la aplicación decidir la partición.

### 3.5 Soporte MCP
- Letta **sí tiene integración MCP nativa y oficial como cliente**: "Letta acts as the host, creating clients that connect to external servers" — el agente puede consumir herramientas/recursos de servidores MCP externos vía protocolo estándar ([docs.letta.com/guides/mcp/overview](https://docs.letta.com/guides/mcp/overview/)).
- Esto es distinto de lo que se busca típicamente ("¿tiene un servidor MCP que exponga la memoria de Letta a otros clientes?") — para ese caso solo se encontraron implementaciones **no oficiales de la comunidad** (`oculairmedia/Letta-MCP-server` en Rust, `@iflow-mcp/letta-mcp-server` en npm), no un servidor MCP mantenido por el equipo core que exponga la memoria de Letta hacia afuera ([github.com/oculairmedia/Letta-MCP-server](https://github.com/oculairmedia/Letta-MCP-server)).

### 3.6 Ciclo de vida
- Los **sleep-time agents** son el mecanismo de consolidación/limpieza: identifican patrones, reorganizan y deduplican bloques, y archivan/podan información obsoleta en segundo plano ([docs.letta.com/guides/agents/architectures/sleeptime](https://docs.letta.com/guides/agents/architectures/sleeptime/)).
- Hay un issue abierto pidiendo **"Archival Memory Deduplication and Consolidation"** como feature — señal de que a agosto 2026 la deduplicación/consolidación automática de archival memory sigue siendo un área en desarrollo activo, no un feature maduro y garantizado out-of-the-box ([github.com/letta-ai/letta/issues/3116](https://github.com/letta-ai/letta/issues/3116)).
- Todo el estado (incluidos bloques de memoria) se versiona vía un sistema tipo git ("MemFS"), dando historial de versiones y filtrado por rango de fechas en todas las capas — es la única de las tres con versionado tipo control de código para memoria ([evidence file](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).
- Debilidades documentadas por comparación de terceros: sin extracción estructurada de entidades/relaciones tipo grafo, sin detección de conflictos entre memorias contradictorias, sin metadata de "por qué"/procedencia de una memoria, y edición directa de memoria (replace/append) sin cadena formal de versiones semántica ([github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md](https://github.com/carsteneu/ai-memory-comparison/blob/main/evidence/letta.md)).

### 3.7 Cómo correr un benchmark local mínimo
1. `docker run -v ~/.letta/.persist/pgdata:/var/lib/postgresql/data -p 8283:8283 -e OPENAI_API_KEY="..." letta/letta:latest` (Postgres + pgvector vienen embebidos) ([docs.letta.com/guides/docker](https://docs.letta.com/guides/docker)).
2. `pip install letta-client` para el SDK Python.
3. Crear dos agentes de prueba (uno por dominio) **o** un agente con bloques/tags separados:
   ```python
   from letta_client import Letta
   client = Letta(base_url="http://localhost:8283")
   agent = client.agents.create(
       model="openai/gpt-4o-mini",
       embedding="openai/text-embedding-3-small",
       memory_blocks=[{"label": "human", "value": "..."}]
   )
   ```
4. Insertar en archival memory con tags: `client.agents.passages.create(agent_id=..., text="Compré una laptop para el proyecto", tags=["expense_tracker"])` y otra con `tags=["finanzas_personales"]`.
5. Buscar con `archival_memory_search(query="¿cuánto gasté este mes?", tags=["finanzas_personales"], tag_match_mode="all")` vs. sin tags, para medir la contaminación cruzada cuando la app no filtra explícitamente — y comparar además contra el escenario "dos agentes separados" para ver el costo de aislamiento perfecto vs. single-agent con tags.

## 5. Veredicto preliminar por alternativa

**mem0 — NO resuelve el aislamiento de contexto nativamente.**
Solo ofrece filtros de metadata de propósito general (`user_id`/`agent_id`/`run_id` + AND/OR/NOT sobre metadata arbitraria) que la aplicación debe diseñar, poblar y aplicar consistentemente en cada inserción y búsqueda. No hay un concepto de "proyecto/dominio" que particione por defecto; si la app olvida el filtro, mem0 mezcla todo — el mismo fallo que motiva KnowledgeOS. Además, la eliminación de graph memory de OSS en 2026 (confirmada en [PR #4805 / issue #6591](https://github.com/mem0ai/mem0/issues/6591)) reduce aún más su capacidad de modelar relaciones entre contextos. Evidencia: [docs.mem0.ai/platform/platform-vs-oss](https://docs.mem0.ai/platform/platform-vs-oss), [deepwiki.com/mem0ai/mem0/11.4-metadata-filtering](https://deepwiki.com/mem0ai/mem0/11.4-metadata-filtering), [GitHub Discussion #3112](https://github.com/mem0ai/mem0/discussions/3112).

**Zep/Graphiti — resuelve el aislamiento de contexto PARCIALMENTE, y es la propuesta técnica más fuerte de las tres, pero con una salvedad organizacional grave.**
El `group_id` de Graphiti da un particionamiento estructural real (subgrafos genuinamente aislados, no solo un filtro post-hoc), lo cual mitiga mejor la contaminación cruzada que un filtro de metadata plano — y viene con supersedencia temporal nativa, el ciclo de vida más maduro de los tres. Pero **no hay resolución automática de ambigüedad entre namespaces** (la partición es dura, no "inteligente"), la combinación intencional de contextos requiere lógica de aplicación, y sobre todo: **no existe un producto "Zep self-hosted" mantenido** — solo el motor Graphiti, que obliga a construir la capa de servicio, multi-tenant y UI desde cero. Es decir, resuelve el problema técnico de aislamiento mejor que las otras dos, pero como "alternativa a adoptar" es realmente "un motor sobre el cual construir", no muy distinto en esfuerzo de ingeniería a construir desde cero con un grafo temporal ya resuelto como cimiento. Evidencia: [help.getzep.com/graphiti/core-concepts/graph-namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing), [blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/).

**Letta — resuelve el aislamiento de contexto PARCIALMENTE, con un patrón distinto (aislamiento por agente, no por namespace de datos).**
La vía robusta es "un agente por dominio", que da aislamiento perfecto pero sacrifica la idea de un único asistente personal con visión completa del usuario (justo lo que KnowledgeOS probablemente quiere: un solo cerebro con particiones internas, no agentes desconectados). La vía fina (`tags` en archival memory) es manual, similar en madurez al filtro de metadata de mem0, y no cubre core memory ni recall memory. No hay concepto de "proyecto" a nivel de plataforma. Punto a favor: el versionado tipo git de toda la memoria y los sleep-time agents dan un ciclo de vida decente, aunque la deduplicación automática todavía está pedida como feature abierta ([issue #3116](https://github.com/letta-ai/letta/issues/3116)). Evidencia: [docs.letta.com/guides/core-concepts/memory/shared-memory](https://docs.letta.com/guides/core-concepts/memory/shared-memory/), [letta.com/blog/conversations](https://www.letta.com/blog/conversations/).

### Conclusión general para la decisión de Fase 0
Ninguna de las tres alternativas resuelve la contaminación entre contextos de forma **nativa y automática** (ninguna detecta ni desambigua vocabulario compartido entre dominios sin que la aplicación diseñe y aplique el particionamiento). La diferencia entre ellas es la **calidad del mecanismo de partición manual** que ofrecen: mem0 da un filtro de metadata blando sobre una colección compartida; Letta da aislamiento fuerte pero a nivel de agente completo (grano grueso) más tags finos solo en archival memory; Graphiti da el particionamiento estructural más limpio (subgrafos verdaderamente aislados vía `group_id`) pero como motor de bajo nivel sin producto de memoria completo alrededor, y con la complicación añadida de que la oferta "self-hosted lista para usar" de Zep como tal ya no existe. Si KnowledgeOS quiere aislamiento de contexto como diferenciador central, **construir esa capa de particionamiento a medida (posiblemente usando Graphiti como motor de grafo subyacente en vez de partir de cero en la capa de grafo) parece más alineado con la hipótesis del proyecto que adoptar mem0 o Letta tal cual**, ya que ninguno de los dos fue diseñado alrededor de "dominios de vida que comparten vocabulario" como problema de primera clase.
